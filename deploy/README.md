# استقرارِ تولید — ست‌شاپ

این سند «دستورالعملِ اجرا روی سرورِ واقعی» است، نه توضیحِ معماری.
هر دستور را به‌ترتیب اجرا کنید؛ در پایان `prod-check.sh` باید همه‌چیز را سبز نشان دهد.

> فرض: یک سرورِ لینوکس (Debian 12 / Ubuntu 24.04) با دسترسیِ `root`،
> دسترسی به اینترنت برای نصبِ بسته‌ها، و یک دامنه.
> تمام مسیرها مطابقِ فایل‌هایِ همین شاخه است؛ اگر مسیرِ دیگری می‌خواهید،
> در سه جا تغییر دهید: `WorkingDirectory` در سرویس‌ها، `DB_URL` در `env`،
> و `root`/`proxy_pass` در تنظیماتِ nginx.

---

## ۰) نصبِ یک‌دستوری (توصیه‌شده)

اگر می‌خواهید همه‌ی مراحلِ زیر (فصل‌های ۱ تا ۷) خودکار انجام شود:

> این فصل برایِ **سرورِ تولید** است (ریشه، systemd، nginx). برایِ اجرایِ پروژه روی
> کامپیوترِ شخصی، `bash setup.sh` در ریشهٔ مخزن کافی است: پیش‌نیازها را نصب
> می‌کند، پایگاه را بیرون ازِ مخزن می‌سازد، مهاجرت‌ها و نشاندن را اجرا می‌کند و
> وب و API را بالا می‌آورد.

```bash
# نخست فقط ببینید چه می‌کند، بی‌آن‌که چیزی تغییر کند:
./deploy/install.sh --dry-run --domain forushgah.example.com

# سپس اجرایِ واقعی:
sudo ./deploy/install.sh --domain forushgah.example.com
```

نصب‌کننده بی‌خطر برای اجرایِ دوباره است و **هرگز فایلِ تنظیماتِ موجود
(`/etc/setshop/env`) را بازنویسی نمی‌کند**. در پایان، `prod-check.sh` را
خودش اجرا می‌کند.

اگر ترجیح می‌دهید هر مرحله را با دست و با آگاهی انجام دهید، ادامه‌ی همین
سند را بخوانید.

## ۱) کاربر، شاخه‌ها و کد

```bash

cd /srv/setshop

# نصبِ وابستگی‌ها — فقط وابستگی‌هایِ اجرا، نه ابزارهایِ توسعه

```

## ۲) پایگاه‌داده

```bash
# شاخه‌ی داده را به‌عنوانِ کاربرِ setshop می‌سازیم (و نه root)
su - setshop -s /bin/bash -c 'PGDATA=/var/lib/setshop/pgdata PGRUN=/run/setshop /srv/setshop/scripts/pg-start.sh'
```

- بدونِ `PGPASSWORD`: فقط سوکتِ یونیکس (`/run/setshop`) — امن و بی‌نیاز از رمز.
- با `PGPASSWORD`: پستگرس روی `127.0.0.1:5433` هم گوش می‌دهد و احرازِ هویتِ
  رمزی (`scram-sha-256`) برقرار است.

مهاجرت‌ها هنگامِ بالا آمدنِ API به‌طورِ خودکار و **اتمیک** اعمال می‌شوند؛
نیازی به اجرایِ دستی نیست (و نباید دو API هم‌زمان بالا بیایند).

## ۴) سرویس‌هایِ سیستمی

```bash
cp /srv/setshop/deploy/systemd/*.service /srv/setshop/deploy/systemd/*.timer /etc/systemd/system/
systemctl daemon-reload

systemctl enable --now setshop-postgres
systemctl enable --now setshop-api
systemctl enable --now setshop-web
systemctl enable --now setshop-backup.timer      # پشتیبانِ شبانه
systemctl enable --now setshop-tax.timer         # ارسالِ خودکارِ صورتحسابِ الکترونیکی
systemctl enable --now setshop-postsale.timer    # صورتحسابِ جامانده + آغازِ گارانتی

systemctl status setshop-postgres setshop-api setshop-web --no-pager
```

نکته‌هایِ طراحیِ این سرویس‌ها:

| تصمیم | چرا |
|---|---|
| `Restart=always` + `StartLimitBurst` | خرابیِ گذرا سرویس را بالا می‌آورد، اما چرخه‌یِ بی‌پایانِ «بالا و افتادن» متوقف می‌شود |
| `ProtectSystem=strict` در سرویسِ API | برنامه حتی اگر نفوذ شود، نمی‌تواند فایل‌هایِ سیستم را بنویسد |
| `OOMScoreAdjust=-500` برای پستگرس | هنگامِ کمبودِ حافظه، آخرین چیزی که کشته می‌شود پایگاه‌داده است، نه اولین |
| سرویسِ وب `Requires=setshop-api` | بدونِ API، پنل بالا نمی‌آید — نمایشِ صفحه‌ی نیمه‌کار بدتر از خطاست |
| پشتیبان با تایمر (نه cron) | `Persistent=true` یعنی اگر سرور در ساعتِ ۳ خاموش بود، پس از روشن شدن جبران می‌کند |
| ارسالِ مالیات با تایمرِ ۱۵ دقیقه‌ای | ارسال نباید به درخواستِ یک کاربر گره بخورد؛ اگر هنگامِ ارسال اینترنت برود، صفحه‌ی مدیر هنگ نمی‌کند و صورتحساب در پایگاه می‌ماند |
| `Type=oneshot` برایِ کارگرِ مالیات | کار کوتاه و تکرارپذیر است؛ فرآیندِ همیشه‌بیکار یعنی مصرفِ حافظه‌ی بی‌دلیل |

## ۵) ساختِ نسخه‌ی تولیدِ وب و نخستین اجرا

```bash
su - setshop -s /bin/bash -c 'set -a; source /etc/setshop/env; set +a; cd /srv/setshop && npm run build:web'
systemctl restart setshop-web
```

داده‌ی نمونه (کالا، کاربرانِ پنل) **فقط** وقتی پایگاه خالی است ساخته می‌شود،
و در تولید مگر با `SEED=1`.

برایِ ایجادِ نخستین مدیر، API را بالا نبرید — یک اسکریپتِ کوچک همین کار را
می‌کند (مهاجرت + ساختِ نقش‌ها و مدیرِ کل، سپس خروج):

```bash
su - setshop -s /bin/bash -c 'set -a; source /etc/setshop/env; set +a; cd /srv/setshop && ADMIN_PASSWORD="رمزِ-قوی" npm run admin:create'
```

اسکریپت بی‌خطر برای اجرایِ دوباره است و دو کاربرد دارد:
نخستین مدیر را می‌سازد، و اگر `ADMIN_PASSWORD` تازه‌ای بدهید، رمزِ مدیرِ کل را
به‌روزرسانی می‌کند (**راهِ بازیابیِ دسترسی** وقتی رمز فراموش شده است).

سپس با همان رمز وارد پنل شوید و کاربرانِ نمونه‌یِ اضافی را غیرفعال کنید.

## ۷-ب) مالیات: ارسالِ خودکار و رفتن به حالتِ واقعی

پس از نصب، سامانه در حالتِ **آزمایشی** است: صورتحساب ساخته، بررسی و در صف
ذخیره می‌شود، اما هیچ اتصالی به سازمان برقرار نمی‌گردد. این عمدی است تا
خطاهایِ داده‌ای (مثلِ نبودنِ شناسه‌یِ کالا) پیش از روزِ رسمی دیده و بسته شود.

وضعیت را این‌گونه ببینید:

```bash
# نتیجه‌ی آخرین دورِ ارسال
journalctl -u setshop-tax -n 20 --no-pager

# زمان‌بندی
systemctl list-timers setshop-tax.timer

# اجرایِ دستی (همان کاری که تایمر می‌کند)
su - setshop -s /bin/bash -c 'set -a; source /etc/setshop/env; set +a; cd /srv/setshop && npx tsx scripts/tax-worker.ts'
```

### کارگرِ پس از فروش (`setshop-postsale.timer`)

پنج وظیفه را هر نیم‌ساعت انجام می‌دهد (پیامک، صورتحساب، گارانتی، پاک‌سازی،
بهداشتِ فایل) — و هر پنج تا «بی‌اثر در تکرار». فهرستِ کامل در سرِ همان اسکریپت
است؛ این‌جا سه نکته‌ای که رویِ سرور به کار می‌آید:

* **صفِ پیامک همین‌جا خالی می‌شود** (`sms_outbox` → کاوه‌نگار/ملی‌پیامک/فراز).
  اگر پیامک‌ها در صف می‌مانند، نخستین جا برایِ فهمیدنِ علت، **دو خطِ اولِ همان
  دور** است: `journalctl -u setshop-postsale -n 20` را بگیر؛ کارگر پیش از هر کاری
  می‌گوید سامانه‌ای انتخاب نشده / «ارسالِ پیامک» خاموش است / کلیدِ دسترسی خالی است /
  `SMS_DRY_RUN` روشن است / «✅ این دور می‌فرستد». متنِ آزاد نیازمندِ **هیچ قالبِ
  تأییدشده‌ای نیست**، به شرطِ این‌که «خطِ پیامک» در پنل (تنظیمات ← پیامک) پر باشد؛
  «شناسهٔ قالب» فقط وقتی لازم است که بخواهی از قالبِ تأییدشده‌یِ سامانه بفرستی.
* رویِ میزبانی که `systemd` ندارد (یا دسترسی‌اش را نداری)، همان کارگر با چرخهٔ
  داخلی بالا می‌آید: `npm run start:worker` (فاصله با `POSTSALE_INTERVAL_SEC`،
  پیش‌فرض ۶۰ ثانیه). دو کارگرِ هم‌زمان — تایمرِ systemd و یکی دستی — چیزی را
  دوباره نمی‌فرستند: برداشتنِ صف با `FOR UPDATE SKIP LOCKED` و مهلتِ `sending` است.
* برایِ یک دورِ فوری (مثلاً بلافاصله پس از پرکردنِ کلید در پنل):
  `npm run worker:once`.
* برای هر ردیفِ پرداخت‌شده‌ای که گارانتی ندارد، گارانتی را **از تاریخِ پرداخت**
  آغاز می‌کند (نه از امروز — تا تأخیرِ کارگر از حقِ مشتری کم نکند).

هر دو وظیفه بی‌اثر در تکرارند: اجرایِ پشتِ‌سرِهم هیچ صورتحسابِ تکراری و هیچ
گارانتیِ دوگانه نمی‌سازد. خروجی یک خط است:

```bash
journalctl -u setshop-postsale -n 20 --no-pager
# پیامک: سامانه‌یِ انتخاب‌شده «کاوه‌نگار»، «ارسالِ پیامک» روشن است.
#    ✅ این دور می‌فرستد. فرستنده: 10008663 · تا 5 تلاش با فاصلهٔ 10 دقیقه
# صف: 3 در انتظار · 0 فرستاده‌شده
# صورتحساب: ۰ ساخته شد (۰ نیازمندِ اصلاح) | گارانتی: ۲۲ آغاز شد (۰ انجام نشد) | پیامک: ۳ فرستاده شد (۰ دوباره در صف، ۰ ناامیدکننده)
```

اگر `timer` غیرفعال شده باشد (بعد از یک `apt upgrade` دیده شده)، خودِ تایمر
همان «پیامکِ نرفته» است: `systemctl list-timers setshop-postsale.timer` را در
بازدیدِ دوره‌ای نگاه کن — یا از پنل، کارتِ «پایشِ صف» که «آخرینِ تکانهٔ صف» و
سکوتِ غیرعادی را نشان می‌دهد.

چرا این کار در لحظه‌یِ پرداخت انجام نمی‌شود؟ چون پرداختِ مشتری نباید به
سامانه‌یِ دولتی، به ثبت بودنِ شناسه‌یِ کالا یا به درستیِ تنظیمات گره بخورد.
فروش انجام می‌شود؛ صورتحساب بعداً ساخته می‌شود و اگر ایرادی داشت، در پنل
با پیامِ روشن دیده می‌شود.

برایِ رفتن به ارسالِ واقعی، این پنج گام لازم است (توضیحِ کامل در
`docs/maliat-moadian.md`):

1. گواهیِ امضایِ الکترونیکی و بارگذاریِ کلیدِ عمومی در کارپوشه‌یِ مالیاتی؛
2. دریافتِ **شناسه‌یِ یکتایِ حافظه‌یِ مالیاتی** و **شناسه‌یِ مشتری**؛
3. قراردادنِ کلیدها در `/etc/setshop/keys/` با دسترسیِ `600` و مالکِ `setshop`
   (کلیدِ خصوصی هرگز در پایگاهِ داده نیست)؛
4. ثبتِ «شناسه‌یِ کالا/خدمت» برایِ هر کالا — از `stuffid.tax.gov.ir`، در پنل:
   **مالیات ← ثبتِ شناسه‌یِ کالا/خدمت**؛
5. تنظیمِ `MOADIAN_MODE=production` و مقادیرِ مرتبط در `/etc/setshop/env`، سپس
   `systemctl restart setshop-api setshop-tax.timer`.

> هشدارِ صادقانه: نشانی‌ها و الگوریتم‌ها را پیش از فعال‌سازی با تازه‌ترین
> مستنداتِ سازمان بسنجید (`MOADIAN_BASE_URL` برایِ تغییرِ نشانی کافی است).

## ۸) پشتیبان‌گیری و بازگردانی

```bash
# دستی
su - setshop -s /bin/bash -c 'set -a; source /etc/setshop/env; set +a; /srv/setshop/deploy/backup.sh'

# دیدنِ زمان‌بندی
systemctl list-timers setshop-backup.timer

# بازگردانی — پایگاه‌داده‌ی کنونی بازنویسی می‌شود (خودش یک نسخه‌ی احتیاطی می‌گیرد)
/srv/setshop/deploy/restore.sh /var/backups/setshop/daily/setshop-20260916-031500.dump
systemctl restart setshop-api setshop-web
```

سه قانون که این اسکریپت رعایت می‌کند:

1. **پشتیبانِ تأییدنشده، پشتیبان نیست** — پس از `pg_dump`، فایل با
   `pg_restore --list` خوانده می‌شود؛ اگر خراب باشد، با پسوندِ `.corrupt`
   نشانه‌گذاری می‌شود تا به آن اعتماد نشود.
2. **دوره‌ی نگه‌داری** — ۳۰ نسخه‌ی روزانه و ۱۲ نسخه‌ی ماهانه؛ بقیه پاک می‌شوند.
3. **کپیِ دوم** — با تنظیمِ `BACKUP_MIRROR_DIR` روی یک دیسکِ دیگر؛
   پشتیبانی که کنارِ خودِ داده‌ها باشد، همراه با داده‌ها از بین می‌رود.

## ۱۰) اگر چیزی خراب شد

| نشانه | نخستین کار |
|---|---|
| سایت بالا نمی‌آید | `systemctl status setshop-web` سپس `tail -100 /var/log/setshop/web.log` |
| خطایِ ۵۰۲ از nginx | `systemctl status setshop-api` و `curl 127.0.0.1:3000/health` |
| «پایگاه‌داده در دسترس نیست» | `systemctl status setshop-postgres` و `tail -50 /var/lib/setshop/pgdata/server.log` |
| API سنگین/هنگ می‌کند | `curl 127.0.0.1:3000/health` را بخوانید: مقدارِ `memory.pressure` پیش از هنگ هشدار می‌دهد |
| ترازِ دفترکل به‌هم خورده | `prod-check.sh` آن را بررسی می‌کند؛ سندِ معکوس ثبت کنید، هرگز چیزی را حذف نکنید |

## ۱۱) گواهِ آزمون — این بسته اجرا شده است، نه فقط نوشته

تاریخِ آزمون: ۱۴۰۵/۰۶/۲۵. همه‌ی مواردِ زیر روی یک پایگاهِ زنده‌یِ ست‌شاپ
(PostgreSQL ۱۷، ۶۵ جدول، ۵ کالا، ۴ کاربر، ۳۱ دسترسی، ۹۰ پیوندِ نقش‌به‌دسترسی)
اجرا و اندازه‌گیری شد.

### ۱۱-۱) پشتیبان‌گیری و بازگردانی (رزمایشِ کامل)

| گام | نتیجه |
|---|---|
| `backup.sh` | ۱۸۰ کیلوبایت در **۰٫۱۷ ثانیه**؛ اثرانگشت (sha256) نوشته شد |
| بررسیِ درستی با `pg_restore --list` | پذیرفته شد |
| `restore.sh` روی پایگاهی تازه | **۰٫۳ ثانیه**؛ اثرانگشت «OK»؛ نسخه‌ی احتیاطی از وضعیتِ پیشین ساخته شد |
| تطبیقِ ردیف‌ها پس از بازگردانی | ۶ جدول، یکی‌یکی برابر: کالاها ۵=۵، تنوع‌ها ۹=۹، کاربران ۴=۴، دسترسی‌ها ۳۱=۳۱، پیوندهایِ نقش ۹۰=۹۰، حساب‌ها ۱۱=۱۱ ✅ |
| نسخه‌ی **خراب** (بریده‌شده به ۴۰ کیلوبایت) | بازگردانی با **کدِ غیرِصفر** شکست خورد و پایگاهِ مقصد با ۰ جدولِ نیمه‌کاره رها شد — یعنی شکست «با صدای بلند» است، نه خاموش ✅ |
| بررسیِ درستی روی همان نسخه‌ی خراب | رد شد (پس آن بررسی در `backup.sh` واقعاً معنادار است) |
| دوره‌ی نگه‌داری | نسخه‌ی ۴۰روزه حذف شد، نسخه‌ی ۱۰روزه ماند ✅ |
| کپیِ دوم با `rsync`ِ **نصب‌نشده** | هشدار داد و ادامه داد؛ پشتیبانِ اصلی سالم ماند (خروجی ۰) ✅ |

### ۱۱-۲) بازبینیِ سلامت (`prod-check.sh`)

اجرا روی همان سرویسِ زنده: **۱۰ سبز از ۱۳**. سه قرمز فقط به این دلیل بود که
در محیطِ آزمون، `systemd` در کار نیست (`setshop-postgres/api/web` با systemctl
پرسیده می‌شوند) — رویِ سرورِ واقعی همان سه هم سبزند.
**کدِ خروجی هنگامِ قرمز بودن: ۱** (مناسب برای CI — تأیید شد).

### ۱۱-۳) اصلاح‌هایی که همین آزمون بیرون کشید

| مورد | پیش از اصلاح | پس از اصلاح |
|---|---|---|
| `backup.sh` و کپیِ دوم | نبودِ `rsync` کلِ پشتیبان‌گیری را شکست می‌داد | هشدار می‌دهد و ادامه می‌دهد؛ نسخه‌ی اصلی سالم می‌ماند |
| مسیرِ سوکت و داده در اسکریپتِ توسعه (`scripts/pg-start.sh`) | زیرِ شاخه‌ی پروژه بود و با بازگردانیِ شاخه، سوکتِ زنده پاک می‌شد (فرآیند زنده، اتصال ناممکن) | بیرون از شاخه‌ی پروژه (`/tmp/setshop-pgrun` و `/tmp/setshop-pgdata`)؛ و اگر فرآیند زنده باشد اما سوکت نباشد، خودش بازنشانی می‌کند |
| نشانیِ چاپ‌شده در `scripts/up.sh` | هنوز مسیرِ قدیمی را می‌گفت | با همان قرارداد هماهنگ شد |

### ۱۱-۴) یک هشدارِ روش‌شناختی درباره‌یِ `/health`

`/health` فقط «زنده‌بودنِ فرآیند» را می‌گوید و عمداً پایگاه‌داده را لمس نمی‌کند؛
بررسیِ وابستگی‌ها بر عهده‌ی `/health/ready` است (درست مانند تفکیکِ liveness و
readiness در کوبرنیتز). پس در نگهبان‌ها و مانیتورینگ، **آمادگی را با
`/health/ready` بسنجید**، نه با `/health` — وگرنه در زمانِ قطعِ پایگاه‌داده،
سامانه «سالم» گزارش می‌شود در حالی که فروش متوقف است. این اتفاق در همین
رزمایش رخ داد و با همین تفکیک شناسایی شد.

# ست‌شاپ (SET) — فروشگاه لوازم جانبی موبایل + انبارداری + حسابداری

> **به‌روزرسانی ۲۰۲۶/۰۹/۲۲:** بازطراحی فروشگاه و مدیریت با حفظ TypeScript/React/Next.js؛ موانع قبلی نوع و مهاجرت رفع شدند. `verify`، ساخت وب و **۸۷۵ آزمون در ۶۲ پرونده** محلی سبز هستند. ۱۶ هشدار امنیتی وابستگی‌ها باقی است. [گزارش طراحی](docs/premium-redesign.md) · [رفع موانع پنل و محدودیت‌ها](docs/admin-stabilization.md).


ساختِ واقعی بر اساسِ سندِ `prampt-enterprise-forushgah-mobile.md` (۱۹۴۷ خط، ۱۱ فاز).
این مخزن از **فاز ۰ (زیرساخت) تا فاز ۵+ (صندوق، حسابداری، تأمین، مالیات)** را
به‌صورتِ اجراشده پیاده می‌کند: فروشگاه، پنل، API، پایگاه‌داده‌ی واقعی، و بسته‌ی
استقرار — همه رویِ همین ماشین بالا آمده‌اند و اندازه‌گیری شده‌اند.

## اجرا

### رویِ کامپیوترِ خودت: یک اسکریپت، همه‌چیز

راهنمایِ گام‌به‌گام — پیش‌نیاز، رفعِ خطاهایِ رایج، فرمان‌هایِ روزمره: **`SETUP-LOCAL.md`**.

```bash
bash setup.sh            # نصبِ پیش‌نیاز → پایگاه → مهاجرت → نشاندن → اجرایِ وب و API
```

اگر پیش‌نیازی نباشد، نصبش می‌کند (PostgreSQL با brew/apt/dnf/pacman/zypper)،
خوشهٔ پایگاه را **بیرون ازِ مخزن** در `~/.setshop/pgdata` می‌سازد، هر ۳۴ مهاجرت
را اعمال می‌کند، و کاتالوگ و کاربرانِ نمونه را **فقط وقتی پایگاه خالی است**
می‌نشاند (تا کالاهایی که فروشنده در پنل ساخته بازنویسی نشوند). سپس
http://localhost:3100 و پنلِ `/admin` را نشان می‌دهد.

| فرمان | کاری که می‌کند |
|---|---|
| `bash setup.sh` | نصب و اجرایِ کامل در حالتِ توسعه (Node ۲۰.۱۱+ لازم است) |
| `bash setup.sh --prod` | ساختِ بهینه (`next build`) و اجرایِ `next start` |
| `bash setup.sh --with-sales` | اجرایِ کامل + سفارش‌هایِ نمونه تا گزارش‌ها عدد داشته باشند |
| `bash setup.sh check` | فقط بررسیِ پیش‌نیازها؛ چیزی نصب و تغییر نمی‌دهد |
| `bash setup.sh install` | فقط پیش‌نیازها و وابستگی‌هایِ npm |
| `bash setup.sh status` / `logs web -f` / `stop` / `seed` | وضعیت، لاگ، خاموشی، فروشِ نمونه |

هرچه راز است (کلیدِ امضایِ نشست، کلیدِ گاوصندوق، توکنِ تماسِ درونی) و هرچه لاگ
و pid است، در `~/.setshop` می‌نشیند و به مخزن نمی‌رود. اجرایِ دوباره بی‌خطر
است: نصب‌شده را دوباره نصب نمی‌کند و سرویسِ زنده را دوباره راه نمی‌اندازد.
برایِ پستگرسِ خودت: `bash setup.sh --db-url=postgres://…`.

### دستی (همان کاری که اسکریپت می‌کند)

```bash
npm ci
npm test                 # ۶۱۵ آزمون در ۴۲ پرونده
npm run db:pg:start      # پستگرسِ واقعی (توصیه‌شده؛ بی‌آن، API سنگین می‌شود)
npm run migrate
TSX_TSCONFIG_PATH=./tsconfig.json ./node_modules/.bin/tsx scripts/seed-catalog.ts
TSX_TSCONFIG_PATH=./tsconfig.json ./node_modules/.bin/tsx scripts/create-admin.ts
DB_URL="postgres://setshop@/setshop?host=$HOME/.setshop/pgrun&port=5433" npm run start:api
npm run start:web        # http://localhost:3100
```

ترتیب مهم است: بی‌`migrate` و نشاندن، فروشگاه خالی است؛ و بی‌`generateStaticParams`
(که در زمانِ **ساخت** از API داده می‌گیرد) کشِ صفحه‌هایِ ویترینی ساخته نمی‌شود —
پس ساخت باید رویِ ماشینِ دارایِ دسترسی به پایگاه انجام شود.

## پنلِ مدیریت (`/admin`)

نخستین بخشی که فروشگاه را **بدون نوشتنِ کد** قابلِ گرداندن می‌کند.

### ورود

| نقش | موبایل | توانایی‌هایِ کلیدی |
|---|---|---|
| مدیر کل | `09120000000` | همه‌چیز |
| فروشنده | `09120000001` | دیدنِ کالا و سفارش، فروش — **تعدیلِ موجودی ندارد** |
| انباردار | `09120000002` | دیدن و **تعدیلِ** موجودی — ثبتِ کالا ندارد |
| حسابدار | `09120000003` | دیدنِ گزارش‌های مالی و **ثبتِ سند و فاکتورِ خرید** — فروشِ حضوری ندارد |

رمزِ همه: `SetShop@1404` (قابلِ تغییر با `ADMIN_PASSWORD`).

نشست در یک کوکیِ `httpOnly` است که فقط از سمتِ سرور نوشته می‌شود؛
مرورگر به آن دسترسی ندارد، بنابراین سرقتِ آن با جاوااسکریپت ممکن نیست.

### بخش‌ها

| نشانی | کاری که می‌کند |

| `/admin/products` | فهرستِ کالاها + **فرمِ ثبتِ کالا** با تنوع‌های پویا و انتخابِ مدلِ گوشی |

### اصلِ طراحیِ دسترسی‌ها

هر مسیر پیش از انجامِ کار دو چیز را بررسی می‌کند:
**توکن معتبر** (وگرنه ۴۰۱) و **اجازه‌ی دانه‌ریز** بر اساسِ «منبع.عمل» (وگرنه ۴۰۳).
دسترسی‌ها در پایگاه‌دادهایند (`roles`, `permissions`, `role_permissions`) و از پنل قابلِ تغییرند؛
هیچ‌کدام در کد ثابت نشده‌اند.

فهرستِ دسترسی‌ها: `product.read/write`، `inventory.read/adjust`، `order.read/write/refund`،
`accounting.read/write`، `pos.sell`، `tax.read/send`، `returns.read/manage`،
`warranty.read`، `user.manage`، `report.read`.

**نکته‌ای که هنگامِ ساخت پیدا شد:** کنترل‌کننده‌ی کاتالوگ از عملِ `edit` استفاده می‌کرد
در حالی که بقیه‌ی سامانه `write` به کار می‌برد. چون مدیرِ کل در `AccessControl.can`
یک مسیرِ میان‌بر دارد، این ناهماهنگی در تست‌هایِ RBAC دیده نمی‌شد و فقط نقش‌هایِ
غیرِ مدیر را — بی‌سروصدا — از ثبتِ کالا محروم می‌کرد. واژگان یکسان شد.

### صندوقِ حضوری (`/admin/pos`)

گردشِ کار: **گشایشِ شیفت → فروش → بستن با شمارشِ نقد**.

| ویژگی | سازوکار |
|---|---|
| فروش فقط از موجودیِ قابل‌فروش | انتخاب‌گر فقط کالاهایی با `available > 0` را نشان می‌دهد |
| جلوگیری از فروشِ تکراری | هر فروش یک `offlineId` یکتا می‌فرستد؛ تکرارِ همان درخواست فروشِ دوم ثبت نمی‌کند |
| مغایرتِ صندوق پنهان نمی‌شود | هنگامِ بستن، «مورد انتظار» در برابر «شمارش‌شده» مقایسه و اختلاف ثبت می‌شود |
| ثبتِ عامل | گشایش، هر حرکتِ نقدی و بستن با شناسه‌ی کاربرِ واقعی ثبت می‌شود |

**یک نقصِ امنیتی که هنگامِ ساختِ این بخش برطرف شد:** مسیرهایِ صندوق هیچ احرازِ
هویتی نداشتند و `userId` را از **بدنه‌یِ درخواست** می‌گرفتند — یعنی هر کسی
می‌توانست شیفت باز کند و «به نامِ هر کسی که بخواهد» بفروشد. اکنون همه‌ی مسیرها
توکن معتبر (۴۰۱) و دسترسیِ `pos.sell` (۴۰۳) می‌خواهند، و شناسه‌ی کاربر **همیشه
از توکن** می‌آید و هرگز از بدنه خوانده نمی‌شود.

سنجشِ انجام‌شده: بدون توکن → ۴۰۱؛ فروشنده → ۲۰۰ و فروش ثبت شد؛
انباردار → ۴۰۳؛ موجودی بلافاصله ۲۵←۲۴ شد؛ بستن با مغایرتِ عمدی اختلافِ
۸۳۰٬۱۰۰ تومان را درست گزارش کرد.


### پنلِ حسابداری (`/admin/accounting`)

فروشندگی به‌تنهایی «حسابداریِ واقعی» نیست؛ چیزی که این پنل اضافه می‌کند،
زنجیره‌ای است که از **فاکتورِ خریدِ تأمین‌کننده** شروع می‌شود، به **انبار**
می‌رود، در **دفترکل** سند می‌خورد، و در **ترازنامه و سود و زیان** دیده می‌شود.

**یک نقصِ امنیتی که هنگامِ ساختِ این بخش برطرف شد:** مسیرهایِ قدیمیِ
`/accounting/*` هیچ احرازِ هویتی نداشتند — هر کسی می‌توانست سندِ حسابداری ثبت
کند یا کلِ دفترکل را بخواند. اکنون هر مسیر توکنِ معتبر (۴۰۱) و دسترسیِ
`accounting.read` یا `accounting.write` (۴۰۳) می‌خواهد، و ثبت‌کننده‌ی سند از
`claims.sub` می‌آید، نه از بدنه‌ی درخواست.

#### ارزش افزوده — چرا جدا از بهای کالاست

در ایران، ارزش افزوده‌ای که روی **خرید** می‌پردازید یک «هزینه» نیست؛
**اعتبار** است که بعداً از مالیاتِ فروش کم می‌شود. اگر آن را در بهای کالا
می‌نشاندیم، دو خطایِ زنجیره‌ای رخ می‌داد:

| اگر اشتباه حساب می‌کردیم | پیامد |
|---|---|
| ارزش افزوده داخلِ بهای کالا | بهای میانگینِ موزون بالا می‌رفت → **سودِ فروش کمتر** نشان داده می‌شد |
| ارزش افزوده نادیده گرفته می‌شد | بدهی به تأمین‌کننده **کمتر از واقع** ثبت می‌شد |

سازوکارِ درست (پیاده‌شده):

```
فاکتور خرید: ۱۰ عدد × ۱۰۰٬۰۰۰ تومان + ۵۰٬۰۰۰ حمل + ۹۴٬۵۰۰ ارزش افزوده
  بدهکار  ۱۰۰۰ موجودی کالا          ۱٬۰۵۰٬۰۰۰ تومان   ← بهای تمام‌شده (بدونِ مالیات)
  بدهکار  ۱۳۰۰ اعتبارِ مالیاتی         ۹۴٬۵۰۰ تومان   ← طلب از دولت، دارایی
  بستانکار ۲۰۰۰ حساب‌های پرداختنی   ۱٬۱۴۴٬۵۰۰ تومان   ← آنچه واقعاً باید پرداخت شود
```

و بهای میانگینِ موزونِ کالا **۱۰۵٬۰۰۰ تومان** می‌ماند، نه ۱۱۴٬۵۰۰ —
سنجشِ انجام‌شده روی پایگاه‌داده‌ی واقعی.

#### هویتِ ایرانیِ تأمین‌کننده و جلوگیری از ثبتِ تکراری

| کنترل | سازوکار |
|---|---|
| شناسه‌ی ملی | الگوریتمِ کنترلیِ رسمی (۱۰ رقم + رقمِ کنترل) — با ارقامِ فارسی هم کار می‌کند |
| کدِ اقتصادی | بررسیِ ساختار (۱۰ تا ۱۴ رقم) |
| فاکتورِ تکراری | قیدِ یکتا روی `(شناسه‌ی ملی، شماره‌ی فاکتورِ تأمین‌کننده)` در **خودِ پایگاه‌داده** → ثبتِ دوباره با `۴۰۹` رد می‌شود |
| تاریخِ شمسی | کاربر «۱۴۰۵/۰۶/۲۰» می‌نویسد؛ در سرور به میلادی تبدیل و در ستونِ `date` ذخیره می‌شود |

چرا قید در پایگاه‌داده و نه فقط در کد؟ چون ثبتِ دوباره‌ی یک فاکتور (سهوی یا
عمدی) یکی از رایج‌ترین راه‌هایِ بزرگ‌نماییِ هزینه است؛ یک شرط در کد را می‌توان
با فراخوانیِ مستقیمِ تابع دور زد، یک قید را نه.

#### فروش هم سند می‌زند (بستنِ حلقه)

تا پیش از این، فقط «خرید» سند می‌ساخت؛ در نتیجه «سود و زیان» همیشه صفر بود و
ارزشِ موجودی در ترازنامه هرگز کم نمی‌شد — یعنی ترازنامه دروغ می‌گفت. اکنون
تأییدِ پرداختِ هر سفارش (آنلاین یا حضوری) در **همان تراکنشی** که کالا از انبار
خارج می‌شود، این سند را می‌سازد:

```
فروشِ حضوریِ ۲ عدد، هر کدام ۲۵۵٬۰۰۰ تومان (میانگینِ خرید ۱۰۵٬۰۰۰ تومان)
  بدهکار  ۱۱۰۰ صندوق و نقد                 ۵۵۵٬۹۰۰ تومان   ← مبلغِ دریافتی
  بدهکار  ۵۰۰۰ بهای کالای فروخته‌شده       ۲۱۰٬۰۰۰ تومان   ← ۲ × میانگین
  بستانکار ۱۰۰۰ موجودی کالا                ۲۱۰٬۰۰۰ تومان   ← خروج از انبار
  بستانکار ۴۰۰۰ درآمدِ فروش                ۵۱۰٬۰۰۰ تومان   ← خالص، بدونِ مالیات
  بستانکار ۲۱۰۰ ارزش افزوده‌ی فروش          ۴۵٬۹۰۰ تومان   ← بدهیِ مالیاتی
```

سنجشِ انجام‌شده روی پایگاه‌داده‌ی واقعی (پستگرس): پیش از فروش، درآمد ۰ و
ارزشِ موجودی ۱٬۰۵۰٬۰۰۰ تومان بود؛ پس از فروشِ ۲ عدد، درآمد ۵۱۰٬۰۰۰،
بهای کالای فروخته‌شده ۲۱۰٬۰۰۰، **سود ۹۰٬۰۰۰ تومان (حاشیه‌ی ۱۷٫۶٪)**،
ارزشِ موجودی ۸۴۰٬۰۰۰ تومان، و ترازنامه همچنان متوازن (اختلاف صفر).

چرا در همان تراکنش؟ چون اگر تراکنشِ جدا بود، ممکن بود کالا از انبار برود اما
سندش ثبت نشود (یا برعکس) و انبار با دفترکل جدا می‌افتاد — دقیقاً همان چیزی
که در عمل، حسابداریِ فروشگاه‌ها را بی‌اعتبار می‌کند.

#### آنچه حسابدار در صفحه می‌بیند

- **پنج کارتِ بالا:** نقد و بانک، ارزشِ موجودی، اعتبارِ مالیاتی، بدهی به تأمین‌کنندگان، سود (زیان)ِ دوره
- **تبِ «نمای کلّی»:** ترازِ آزمایشی (با نشانِ تراز/ناتراز)، ترازنامه (سه ستون)، سود و زیان با حاشیه‌ی سود
- **تبِ «دفتر روزنامه»:** ثبتِ سندِ دستی با **ترازسنجِ زنده** (تا جمعِ بدهکار و بستانکار برابر نباشد، دکمه‌ی ثبت غیرفعال است) + فهرستِ اسناد با ردیف‌هایِ بازشونده و دکمه‌ی «برگشت»
- **تبِ «فاکتورِ خرید»:** فرم با ردیف‌هایِ پویا، پیشنهادِ خودکارِ ارزش افزوده (۹٪)، و خلاصه‌ی مالی **پیش از ثبت**
- **تبِ «ارزشِ موجودی»:** بهای میانگینِ موزون و ارزشِ هر کالا — همان عددی که در ترازنامه می‌نشیند

سنجشِ انجام‌شده (روی پستگرسِ واقعی، با نقشِ حسابدار): فاکتور `PINV-1405-000001`
با سندِ سه‌ردیفه‌ی `JV-1405-000001` ثبت شد؛ ثبتِ دوباره‌ی همان فاکتور → ۴۰۹؛
سندِ غیرتراز → ۴۲۲؛ برگشتِ سند، سندِ معکوس ساخت و اصل را حذف نکرد؛
ترازنامه متوازن (اختلاف صفر)؛ فروشنده در همه‌ی مسیرهایِ حسابداری → ۴۰۳.

### تعدیلِ موجودی

تنها نقطه‌ای که می‌توان عددِ موجودی را تغییر داد.
دو قاعده که در تراکنش با `FOR UPDATE` اعمال می‌شوند:

1. موجودی هرگز منفی نمی‌شود → `۴۲۲` (نه خطایِ داخلیِ ۵۰۰)
2. موجودی نمی‌تواند از مقدارِ **رزرو‌شده** کمتر شود → `۴۲۲`

هر تغییر در `stock_movements` با شناسه‌یِ کاربرِ عامل ثبت می‌شود،
بنابراین همیشه می‌توان فهمید چه کسی و چرا موجودی را تغییر داده است.

## حافظه و سنگینی — چرا و چه باید کرد

اندازه‌گیری‌شده روی همین دستگاه (کل: ۱۹۸۴ مگابایت).

### اندازه‌گیریِ مرحله‌به‌مرحله (روی یک دستگاهِ ۱۹۸۴ مگابایتی)

| مرحله | API | نکست | حافظهٔ در دسترس |
|---|---|---|---|
| ۱. وضعیتِ نخست (نکست توسعه + PGlite) | ~۳۵۰ MB | **~۷۵۰ MB** | **~۳۷۰ MB** |
| ۲. پس از اجرایِ تولیدِ نکست | ۴۰۴ MB | **~۹۴ MB** | ~۹۹۰ MB |
| ۳. پس از جدا کردنِ پایگاه‌داده | **۱۸۵ MB** | ~۱۰۲ MB | **~۱۱۰۰ MB** |

یعنی مجموعاً **حدود ۳ برابر حافظهٔ آزاد بیشتر**، و API نزدیکِ **۲ برابر سبک‌تر**.

### علتِ اصلی: پایگاه‌داده درونِ فرآیند

PGlite یک موتورِ کاملِ پستگرس است که به‌صورتِ WASM **داخلِ نود** اجرا می‌شود.
اندازه‌گیری: یک نودِ بی‌آلایش ۳۸ مگابایت بود؛ با بارشدنِ موتورِ PGlite پرید روی
**۸۰۰ مگابایت**. در فرآیندِ واقعی هم همین نسبت برقرار بود:

```
"memory": { "rssMb": 404, "heapUsedMb": 38 }   ← با PGlite
"memory": { "rssMb": 185, "heapUsedMb": 35 }   ← با پستگرسِ واقعی
```

هیپِ جاوااسکریپت در هر دو حالت حدود ۳۵ مگابایت است — **تمامِ تفاوت از
پایگاه‌داده می‌آید**، و چون حافظهٔ WASM بیرون از هیپ است، `‎--max-old-space-size`
اصلاً آن را نمی‌بیند و جلوی هنگ را نمی‌گیرد.

### چرا «هنگ» می‌کرد نه اینکه خطا بدهد

PGlite کار را **همگام** در حلقهٔ رویداد انجام می‌دهد. وقتی حافظه فرو می‌ریزد،
فراخوانِ WASM گیر می‌کند و چون همگام است **کلِ حلقهٔ رویداد قفل می‌شود** → همهٔ
درخواست‌ها همزمان وقت‌می‌خورند. سپس کشندهٔ OOM فرآیند را می‌کشد — و چون هنگامِ
نوشتن کشته می‌شود، شاخهٔ داده خراب می‌گردد (همان مشکلی که در بخشِ پایایی آمد).

### راه‌اندازیِ پستگرسِ واقعی (توصیه‌شده)

رویِ ماشینِ تازه، `bash setup.sh` همه‌یِ این‌ها را یک‌جا انجام می‌دهد
(نصبِ پستگرس، خوشه، مهاجرت، نشاندن، اجرا). دستی:

```bash
npm run db:pg:start     # ساختِ خوشه و آغاز به کار (نخستین اجرا)
npm run start:pg        # راه‌اندازیِ پایگاه + API با آن
npm run db:pg:stop      # توقف
```

سه پیامدِ مثبتِ همزمان: حافظهٔ API نصف می‌شود، پایگاه در برابرِ کشته‌شدنِ
ناگهانی مقاوم می‌شود (WAL)، و امکانِ پشتیبان‌گیریِ استاندارد فراهم می‌گردد.

### دستورها

```bash
npm run web          # ساخت + اجرایِ تولید  ← پیش‌فرضِ توصیه‌شده
npm run build:web    # فقط ساخت
npm run start:web    # فقط اجرا (باید پیش‌تر ساخته شده باشد)
npm run dev:web      # حالتِ توسعه (سنگین؛ فقط هنگامِ تغییرِ رابط)
```

مسیرِ `GET /health` اکنون حافظه را هم گزارش می‌کند
(`pressure: normal | high | critical`) تا فشار **پیش از** هنگ دیده شود.

### خلاصه: چه چیزی درست شد

1. ✅ **پایگاه از فرآیند جدا شد** — `npm run start:pg` (پستگرسِ واقعی، WAL،
   مقاوم در برابرِ کشته‌شدن). API از ۴۰۴ به ۱۸۵ مگابایت رسید.
2. ✅ **نکست در حالتِ تولید اجرا می‌شود** — از ۷۵۰ به ~۱۰۰ مگابایت.
3. ⚠️ **تست‌ها را همزمان با دو سرور اجرا نکنید** — هر فایلِ تست یک نمونهٔ
   پایگاه بالا می‌آورد؛ این همان چیزی بود که یک‌بار دستگاه را کاملاً قفل کرد.

### پایگاه‌داده و ماندگاریِ داده

پیش‌فرض دیگر حافظه‌ی موقت نیست — داده روی دیسک می‌ماند و با بستنِ سرور از بین نمی‌رود.
سه حالت، تنها با یک متغیرِ محیطی:

| مقدارِ `DB_URL` | رفتار | کاربرد |
|---|---|---|
| `memory://` | پایگاه در حافظه، پس از خاموشی پاک می‌شود | فقط تست‌ها |
| `./.data/pg` (**پیش‌فرض**) | PGlite روی دیسک، داده می‌ماند | توسعه‌ی روزمره |
| `postgres://user:pass@host:5432/db` | PostgreSQL واقعی از طریق `pg.Pool` | تولید |

داده‌ی نمونه تنها زمانی بارگذاری می‌شود که جدولِ `products` خالی باشد؛
بنابراین اجرایِ دوباره، داده‌ی شما را بازنویسی نمی‌کند
(و در حالتِ `production` مگر با `SEED=1` اصلاً اجرا نمی‌شود).

**سنجشِ انجام‌شده:** یک سفارشِ ۳ عددی ثبت شد (موجودی: ۵ موجود ← ۳ رزرو، ۲ قابل‌فروش)،
سپس سرور با `SIGTERM` ایمن خاموش و دوباره بالا آمد؛
رزروِ ۳ تا همچنان برقرار بود و شماره‌ی سفارشِ بعدی `ORD-1405-000002` شد (نه `000001`) —
یعنی هم موجودی و هم شمارنده‌ی اسناد روی دیسک مانده بودند.

> **هشدارِ مهم — چرا تولید باید PostgreSQL واقعی باشد:**
> در این محیط یک‌بار فرآیندِ سرور بر اثرِ کمبودِ حافظه هنگامِ نوشتن کشته شد و
> شاخه‌ی فایلِ PGlite خراب گردید (`PGlite failed to initialize properly`)؛
> با خاموشیِ ایمن (`SIGTERM`) چنین اتفاقی نمی‌افتد.
> PGlite روی دیسک برای توسعه خوب است، اما **تحملِ خرابیِ ناگهانی (crash recovery) ندارد**.
> برای تولید، `DB_URL` را به PostgreSQL واقعی بدهید که با WAL از چنین وضعیتی عبور می‌کند،
> و همیشه پشتیبانِ دوره‌ای داشته باشید.

## تصمیماتِ کلیدی که در کد ثبت شده‌اند

1. **همه‌ی مبالغ `BIGINT` به ریال**؛ نمایش به تومان فقط در لایه‌ی نمایش.
2. **تخفیف پیش از مالیات و مالیات در سطحِ ردیف** (بخش U) — با تست قفل شده.
3. **توزیعِ دقیق (`allocate`)**: مجموعِ خروجی دقیقاً برابرِ ورودی؛ هیچ ریالی گم نمی‌شود.
4. **شماره‌گذاری با `INSERT … ON CONFLICT DO UPDATE … RETURNING`**؛ ۵۰ فراخوانِ همزمان → بدون تکرار.
5. **همه‌ی زمان‌ها `timestamptz` به UTC**؛ شمسی فقط در نمایش.
6. **قیدِ موجودی در خودِ پایگاه‌داده** (`reserved <= on_hand`) — جلوگیری از Oversell
   حتی اگر کدِ برنامه اشتباه کند. این مستقیماً همان دردِ «لغوِ سفارش به‌دلیل ناموجودی» را هدف می‌گیرد.
7. **هیچ موجودیتِ تراکنشی حذف نمی‌شود**؛ `stock_movements` فقط الحاقی است.
8. **هر خطا یک کدِ ثابت و یک `traceId`** دارد.
9. **توکنِ تازه‌سازی می‌چرخد** و استفاده‌ی مجدد از توکنِ مصرف‌شده، **کلِ خانواده را می‌بندد** (نشت را مهار می‌کند).
10. **محدودیتِ شعبه روی داده**: کاربر فقط نقشِ شعبه‌ی خودش را دارد — از نشتِ داده بین شعبه‌ها جلوگیری می‌کند.
11. **سازگاری یک رابطه‌ی جدولیِ دقیق است، نه متنِ آزاد**: فیلتر بر اساسِ مدل گوشی در سطحِ پایگاه‌داده
    انجام می‌شود و هر تنوع فقط کالای مخصوصِ همان مدل را برمی‌گرداند (در دِمو: آیفون ۱۳ پرو →
    `CS-13P-BLK`، گلکسی S23 → `CS-S23-BLK`).
12. **پاسخِ سازگاری سه‌حالته است**: «می‌خورد» / «نامعلوم» / «اعلام‌نشده».
    ندانستن، از حدس زدن بهتر است — و کالاهای اعلام‌نشده در پنل گزارش می‌شوند.

## استقرارِ تولید

```bash
bash setup.sh --prod                # اجرایِ محلیِ نزدیک به تولید (بی‌nginx و بی‌سرویسِ سیستمی)
sudo ./deploy/install.sh            # نصبِ کامل (کاربر، پایگاه، سرویس، nginx، پشتیبان)
sudo ./deploy/install.sh --dry-run  # فقط نشان بدهد چه خواهد کرد، بی‌آنکه تغییری بدهد
./deploy/prod-check.sh              # بررسیِ سلامت پس از هر انتشار (خروجیِ غیرصفر = قرمز)
```

**سه تنظیمِ نشانیِ مشتری** (چون هم سقف‌ها و هم ردپایِ ممیزی به آن گره‌ خورده‌اند):

| کلید | جایِ کار | پیش‌فرض | معنا |
|---|---|---|---|
| `TRUSTED_PROXY_IPS` | API | `127.0.0.1,::1` در تولید، تهی در توسعه | نشانی‌هایی که حق دارند بگویند «مشتری از این IP است» (`X-Real-IP` / `X-Forwarded-For`) |
| `TRUST_WEB_CLIENT_IP` | API | `true` | پذیرشِ `x-set-client-ip` از لایهٔ وب (نیازمندِ `x-set-internal`) |
| `TRUST_XFF` | وب | تهی | اگر nginx شما تنها `X-Forwarded-For` می‌فرستد، `1` بگذارید؛ تا آن‌جا `x-forwarded-for`ِ خامِ کلاینت خوانده نمی‌شود |

بی‌nginx و بی‌این تنظیم‌ها، سیستم «fail closed» است: همهٔ ترافیک از نشانیِ
خودِ سرور شمرده می‌شود — پس سقف‌ها درست‌اند، ولی به ازایِ هر خریدار جدا نیستند.

جزئیات، پشتیبان‌گیری و بازگردانی، و رفعِ اشکال: `deploy/README.md`.

## تصمیم‌های فنی (۱۶ تا ۲۰)

۱۶. **صندوقِ حضوری همان موتورِ فروش است** — هیچ منطقِ جداگانه‌ای برای موجودی یا قیمت در POS نیست؛
    تفاوت فقط در کانال (`pos`)، پرداختِ همان‌لحظه‌ای، و وابستگی به «شیفت».
۱۷. **یک شیفتِ باز به ازای هر انبار** — با ایندکسِ یکتایِ شرطی
    (`UNIQUE (warehouse_id) WHERE status='open'`)؛ این قید در پایگاه‌داده است، نه در کد.
۱۸. **فروشِ آفلاین با شناسه‌ی یکتا** — `offline_id` به‌ازای هر شیفت یکتاست و کلیدِ یکتایی می‌سازد،
    پس همگام‌سازیِ دوبارهِ یک دستگاه هرگز دو فروش ثبت نمی‌کند.
۱۹. **بهای تمام‌شده با میانگینِ موزون + توزیعِ دقیق** — هزینه‌های جانبیِ فاکتورِ خرید
    (حمل، گمرک) با الگویِ largest-remainder بین ردیف‌ها پخش می‌شود؛ هیچ ریالی باقی نمی‌ماند
    و مجموعِ سهم‌ها دقیقاً برابرِ کل است.
۲۰. **پنجره‌ی رزروِ حضوری ۱۵ دقیقه است، نه ۱ دقیقه** — اگر کارگرِ آزادسازیِ رزروها
    دقیقاً میانِ «ایجاد سفارش» و «پرداخت» اجرا شود، نباید فروشی را که در جریان است
    باطل کند. این یک رقابتِ واقعی بود که در اجرایِ آزمون‌ها خود را نشان داد و
    با تستِ بازگشت قفل شد: `releaseExpiredReservations` روی فروشِ حضوری صفر برمی‌گرداند.
۲۱. **سند هرگز حذف نمی‌شود** — اصلاح فقط با سندِ معکوس؛ ردیفِ سند یا بدهکار است یا بستانکار،
    و تراز بودن هم در کد و هم در قیدِ پایگاه‌داده کنترل می‌شود.

| `/device/:id` | **فقط** کالاهای سازگار با آن مدل گوشی — هسته‌ی مزیتِ رقابتی |
| `/products/:slug` | جزئیات: تصویر، تنوع‌ها، موجودیِ واقعی، مدل‌های سازگار، افزودن به سبد |
| `/cart` | سبد + فرمِ اطلاعاتِ گیرنده + ثبتِ سفارش |

ویژگی‌هایِ تحقق‌یافته:

- **رندر در سرور (RSC)** — صفحه با محتوا به مرورگر می‌رسد، نه با چرخ‌دنده‌ی بارگذاری؛
  این یک برتریِ مستقیم بر فروشگاه‌هایِ قالبیِ سنگین است.
- **هیچ داراییِ خارجی** — فونتِ وزیرمتن (متن‌باز) در `apps/web/public/fonts` میزبانی می‌شود؛
  سایت با اینترنتِ بین‌المللِ قطع‌شده هم کامل بالا می‌آید (الزامِ بخش AA).
- **لایه‌ی طراحیِ جداشده** — همه‌ی رنگ، فاصله، اندازه و شعاع فقط در
  `apps/web/src/app/globals.css` تعریف شده است. هیچ مقداری در کامپوننت‌ها سفت‌کد نیست،
  پس تحویلِ قالب/فیگما فقط همان یک فایل را تغییر می‌دهد.
- **پروکسیِ `/api`** — مرورگر فقط با مسیرِ نسبی صحبت می‌کند (rewrite در `next.config.mjs`)؛
  بنابراین هیچ تماسِ مستقیمی با پورتِ سرویسِ داخلی وجود ندارد.
- **مبالغ با ارقامِ فارسی و یکانِ تومان**، و کلاسِ `.num` برای این‌که ارقام در متنِ
  راست‌چین جابه‌جا نشوند.

### تصویرِ کالاها

تصاویر با مسیرِ **نسبی** در جدولِ `product_images` ذخیره می‌شوند و هیچ
درخواستی به اینترنت نمی‌رود. دو راه برای آمدنِ تصویر وجود دارد:

- **بارگذاری از پنل** (توصیه‌شده): فروشنده عکس را می‌کشد و رها می‌کند؛
  سامانه سه اندازه (`full` ۱۶۰۰، `card` ۶۰۰، `thumb` ۲۰۰) و یک پیش‌نمایشِ
  تار می‌سازد و در `var/media/` می‌نشاند (مسیرِ قابلِ تنظیم با `MEDIA_DIR`).
  جزئیات: `docs/resaneh.md`.
- تصویرِ نشانی‌دار (قدیمی): همان `/products/<slug>.jpg` در
  `apps/web/public/products/` — برای کالاهایِ داده‌ی نمونه، بی‌تغییر مانده. تصاویرِ فعلیِ داده‌ی نمونه با هوشِ مصنوعی
ساخته شده‌اند و **جایگزینِ عکاسیِ واقعی نیستند**؛ برای فروشِ جدی، عکاسیِ
حرفه‌ایِ محصول لازم است (رایج‌ترین عاملِ ادراکِ کیفیت در فروشگاه اینترنتی).

> نکته: Next خروجیِ واکشی را روی دیسک کش می‌کند (`.next/cache`). پس از تغییرِ
> داده‌ی نمونه، این پوشه را پاک کنید تا صفحات با داده‌ی تازه رندر شوند.

### در انتظارِ تصمیمِ طراحی

کامپوننت‌ها و منطقِ داده کامل است، اما **هویتِ بصریِ نهایی تعمداً ساده نگه داشته شده**،
چون کیفیتِ ادراک‌شده در فروشگاه اینترنتی بیش از هر چیز به دو چیز وابسته است که از کد
نمی‌آیند: **عکاسیِ حرفه‌ایِ محصول** و **طراحیِ بصریِ اختصاصی**.
تا پیش از تأمینِ یکی از این دو منبع، پوسته‌ی فعلی یک «وضعیتِ تمیز و بی‌ادعا» است که
جایگزین کردنش هزینه‌ای ندارد:

۱. فایلِ فیگما از طراح ← تبدیلِ مستقیم به متغیرهایِ `globals.css`؛
۲. یا یک قالبِ راست‌چینِ باکیفیت ← پیاده‌سازی با همین کامپوننت‌ها.

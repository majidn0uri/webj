# مدیریتِ مشتریان در پنل

چرا این بخش؟ چون مشتری از ۰۱۷ به بعد یک «حسابِ کاربری» دارد — اما هیچ
ابزاری برایِ دیدن و اداره‌اش در پنل نبود. اگر مشتری زنگ می‌زد و می‌گفت
«سفارشم را نمی‌بینم»، راهی جز رفتنِ مستقیم به پایگاهِ داده نبود: همان
وابستگی به برنامه‌نویس که قرار نبود وجود داشته باشد.

## ۱. جایی که می‌سازد

| فایل | نقش |
|---|---|
| `packages/db/migrations/018_customer_management.sql` | سه دسترسیِ تازه + ستونِ `customer_sessions.revoke_reason` |
| `apps/api/src/admin-customers.controller.ts` | سه مسیر: فهرست با جستجو، پرونده، ویرایش، مسدودسازی |
| `apps/web/src/lib/customer-actions.ts` | کنش‌هایِ سرور (نشانه در کوکیِ HttpOnly است) |
| `apps/web/src/app/admin/(panel)/customers/page.tsx` | فهرست با جستجویِ شماره/نام |
| `apps/web/src/app/admin/(panel)/customers/[id]/page.tsx` | پرونده |
| `apps/web/src/components/admin/customer-dossier.tsx` | پرونده در یک نگاه + ویرایش + مسدودسازی |

## ۲. جستجو: چطور شماره پیدا می‌شود

اپراتور شماره را ممکن است با ارقامِ فارسی، با فاصله، با خطِ تیره یا با `۰۹۱۲`
بنویسد. جستجو فقط رقم‌ها را می‌بیند و با `regexp_replace` روی ستون اعمال
می‌کند؛ بنابراین `۰۹۱۲ ۳۳۳ ۴۴۵۵` و `9123334455` و `+989123334455` همگی یک
نتیجه می‌دهند. اگر جستجو همان‌طور که تایپ شده انجام می‌شد، مشتری «هست اما
پیدا نمی‌شود» — بدترین تجربه برای کسی که پشتِ خط منتظر است.

جستجو با فرمِ GET ساده است (نه جاوااسکریپت): ماندنِ عبارت در نشانی یعنی
بتوان آن را برایِ همکار فرستاد یا در تاریخچه پیدا کرد.

## ۳. دسترسی‌ها (تفکیکِ وظایف)

| نقش | read | write | deactivate |
|---|:--:|:--:|:--:|
| مدیر کل | ✓ | ✓ | ✓ |
| مدیر شعبه | ✓ | ✓ | ✓ |
| حسابدار | ✓ | ✓ | — |
| فروشنده | ✓ | — | — |
| انباردار | ✓ | — | — |

چرا سه دسترسی و نه یکی؟ چون «دیدنِ مشتری»، «تغییرِ سقفِ اعتبار» و «بستنِ
حساب» سه مسئولیتِ متفاوت است. اگر یکی می‌شد، فروشنده‌ای که فقط باید جوابِ
تلفن بدهد می‌توانست اعتبارِ مشتری را بالا ببرد یا حسابش را ببندد.

## ۴. مسدودسازی: حذف نمی‌کنیم

مسدود کردن فقط **دسترسی** را می‌گیرد، نه تاریخچه را — چون مشتری سفارش و سندِ
مالی دارد. در همان لحظه:

1. `customers.is_active = false` و دلیل ثبت می‌شود؛
2. همه‌ی نشست‌هایِ باز باطل می‌شوند (`revoked_at` + دلیلِ
   `account_deactivated`)؛
3. ورودِ بعدی — چه با کدِ پیامک، چه با گذرواژه — رد می‌شود.

مسدودی **پس از** درستیِ کد/گذرواژه بررسی می‌شود، نه پیش از آن: اگر پیش از آن
رد می‌کردیم، پیامِ «حساب مسدود است» به هر کسی که شماره را می‌داند می‌گفت این
شماره حساب دارد (نشتِ اطلاعات).

## ۵. دو نقص که رزمایش بیرون کشید

| نقص | چرا مهم بود | اصلاح |
|---|---|---|
| پیامِ خطایِ سامانه دور انداخته می‌شد | پاکتِ خطا `{ error: { message } }` است اما کد از ریشه می‌خواند؛ پیامِ «حساب مسدود است» به «کد درست نبود» تبدیل می‌شد و مشتری بی‌پایان کد می‌گرفت | `apiMessage()` پیام را از پاکتِ استاندارد می‌خواند |
| بدنه‌ی پاسخ دو بار خوانده می‌شد | پاسخ یک جریان است؛ خواندنِ دوم همیشه تهی است، پس پیامِ واقعی باز هم گم می‌شد | یک بار خواندن، استفاده در هر دو جا |

## ۶. گواهِ اجرا (۱۴۰۵/۰۶/۲۵)

با مرورگرِ واقعی و ورودِ مدیر کل:

| گام | نتیجه |
|---|---|
| ثبتِ‌نامِ مشتری در فروشگاه | موفق (کدِ پیامک در حالتِ توسعه) |
| جستجو با شماره در پنل | مشتری در یک ردیف یافت شد |
| باز کردنِ پرونده | کارت‌ها: سفارش‌ها، خریدِ کل، آدرس‌ها، علاقه‌مندی‌ها |
| ویرایش (یادداشت + سقفِ اعتبار ۵٬۰۰۰٬۰۰۰ تومان) | «پرونده به‌روزرسانی شد.» |
| مسدودسازی | «حساب مسدود شد و نشست‌هایِ باز باطل شدند.» (۱ نشست باطل شد) |
| نشستِ مشتریِ نشسته | همان لحظه باطل شد |
| ورودِ دوباره با کدِ درست | «حساب شما مسدود است: درخواستِ خودِ مشتری» |

آزمون‌هایِ خودکار: `packages/shopper` **۲۲ آزمون** (۵ تایِ تازه برایِ
مسدودسازی: کدِ درست هم راه نمی‌دهد، دلیل در پیام می‌آید، نشستِ پیشین بی‌اعتبار
می‌شود، ورود با گذرواژه هم بسته است، و ابطالِ نشست‌ها ثبت می‌شود).

## ۷. یادداشتِ فنی برایِ رزمایش با مرورگر

کلیکِ برنامه‌ای (`element.click()` درونِ صفحه) روی دکمه‌یِ `type="submit"`
در React رویدادِ submit را نمی‌سازد؛ در آزمون باید از کلیکِ واقعیِ موس
(`ElementHandle.click()`) استفاده کرد. این نکته چند بار آزمون را به خطا
انداخت و وقت گرفت — ثبت می‌شود تا دوباره تکرار نشود.
